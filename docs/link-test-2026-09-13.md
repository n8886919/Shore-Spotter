## GPS 與證據限制

- 兩端全部快照均沒有有效定位，GPS 模式不可用；未驗證座標精度、速度／方向、α 外推
  或機械追蹤效果。DATA 的固定原點 24°N／121°E 是 fix=false 時的編碼值，不是實際位置。
- Client 有 RMC／GGA epoch，間隔 1000 ms；DATA 來源 age 交替 190／690 ms，證明
  500 ms RF 排程會重送同一個 GNSS epoch，沒有把重送當成新定位。
- Server 未建立 RMC／GGA epoch。本輪 rejected_sentences 增加 120、ignored 增加 480，
  checksum_errors 未增加；有正常 NMEA 流，但缺少原始 RMC／GGA，不能確定拒收原因。
  無定位且 UTC 空白的句子也會被目前 parser 拒收，不能直接把此計數當成 UART 損壞。
- Server `ack_sent` 表示發送完成。現有 DIAG 沒有 Client 的 ACK 接收計數，
  **尚不能證明 Client 收到了這 15 個 ACK**；需要 Client 串口紀錄或後續診斷欄位佐證。

## 發現的時序問題

第 13 秒的觀察中，Server HTTP 單次最大耗時由約 32 ms 增至 **211.34 ms**，
控制服務最大間隔增至 **212 ms**；下一筆 GNSS 快照顯示 Server backlog_drops 由 0 變 1。
Client backlog 保持 0，期間没有新增 LoRa 序號缺口。Server 的 200 ms GNSS 防積壓規則
已生效，但此 HTTP 停頓的根因仍待定位；不能因無線收包正常就宣稱控制時序沒有問題。

當時主機 `/api/debug` 端到端耗時為 525.71 ms，包含網路與排程，與板上 HTTP 的
211.34 ms 是不同量測。此次輪詢每秒依序讀三個 API，每五秒另讀 log，與手機瀏覽器
排程不完全相同；尚未量測實際動作時的影響。本次記錄問題，未修改韌體。

原始採樣與逐包解碼保留在本機暫存測試產物，未加入 Git；包含運行資料，不作為原始碼。

### 尚存在的網頁端等待

**不能描述為零 HTTP 問題**：主機 transport 有 3 次 2 秒 timeout／AbortError（status
兩次、track 一次）；另有 debug／log 各一次在共用排程中等到逾時，匯出記為 2 次除錯
錯誤。3 次相鄰取樣間隔約 3 秒；所有輪詢隨後自行恢復，事件增量補回，沒有事件 ID
缺口或 Server 重開機。成功 debug 的主機 RTT 最大仍達 1,949 ms。

這段等待期間，板上 HTTP 長耗時與控制間隔計數沒有增加，因此不能把它說成已重現
原先 211.34 ms 的同步 `handleClient()` 停頓；目前只能定位為板上已量測處理之外的
端到端等待／排隊連鎖，尚未確定是 Wi-Fi、主機 transport 或其他環節。單頁序列化
不會消除所有網路等待，也不能限制其他手機／分頁同時連線。
