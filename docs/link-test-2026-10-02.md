## 已確認

- USB/esptool：V4 為 ESP32-S3、16 MB flash、2 MB QSPI PSRAM；runtime FEM probe 是 KCT8103L。
  這支持 V4.3 FEM 路徑，但無法由 USB 確認板面細分版號。
- V4 原廠 16 MiB 備份與裝置 digest 相符；最後 app-only 寫入 1,585,872 bytes，工具確認 hash 一致，NVS 配對保留。
- T096 以 application-only serial DFU 燒錄，保留 bootloader；實機 Client ID 為 F035，boot `D9054E5D`。
- Web `test` 指令由 pending 到 STATE confirmed 約 9.2 秒。連續 60.9 秒新增 99 個 probe，
  counter 缺號 0，最後 RSSI -52 dBm／SNR 8.8 dB，最大 probe 間隔 1570 ms。
  最大間隔含 STATE airtime 與接收窗，不能直接當封包遺失；counter 只涵蓋已觀測區間。
- Station 重燒重啟後，NVS 綁定仍是 F035，從 Client STATE 同步 command ID 2。
  `start` #3 約 6.25 秒確認 tracking，`stop` #4 約 6.51 秒確認 ready；最終保持 ready。
- USB 供電時 `store` 回 409；不合法手機位置回 400。
- RF 測試期間 `rf_alive=true`，`data_fresh=false`、DATA FPS 0、Client fix 0；未用假 GPS 讓追蹤過 gate。
  Start/stop 後 Servo 命令與目標都維持 90°，不代表已量測實體角度。

## 後續程式對照：T096 的 2 Hz 缺口

對照移植前 `efcded0` 的一般 LilyGO v5：GNSS 設定為 500 ms RMC/GGA，
依實際新 epoch 排程 DATA，非阻塞 TX、保留 airtime/guard，忙碌時只選最新樣本而不回補舊位置。
遙測／診斷也占用 airtime，所以不是每個 DATA 到達間隔都保證 500 ms。
`FIELD_DIAGNOSTIC`／trip profile 則明確設定 1000 ms，不能與一般版混稱。

T096 移植目前只 enable GNSS 並開 115200 UART，未加入 receiver 專用的 2 Hz 設定／實測率監控。
追蹤／RF 測試每約 5 秒送 STATE，之後不論是否有命令都開最多 800 ms RX；
`air != Idle` 期間不會送 DATA／probe。GNSS UART 仍持續讀取，這是 RF 發送空檔，並非 CPU 停讀 GPS。
因此即使未來餵入穩定 2 Hz 定位，現有排程仍不能維持連續 500 ms 發送。
這是已確認的移植缺口，不是已診斷的 GNSS 不穩定；RF test 模式不送定位 DATA，本來就會顯示 DATA FPS 0。
待修正需分開驗證 receiver 新 epoch 頻率、DATA 實際送達頻率及控制接收占用時間。
