# 2026-09 至 10 月測試結論與 2026-11-25 資料整理

本文件將舊 `shore-spotter-debug` 的結論帶入 Git，避免只存在單一電腦。
這是既有報告的整理，**不是本日重新外測或重新計算 raw data**。
使用者已表示測試 raw data 不必留；結論、原因、限制與下一步必須可從遠端 Git 取回。
未解決問題不因清理資料變成已解決，摘要和 hash 也不能替代原始資料重新分析。

## 保留的結論

### 1. GPS 偏差、RF 與地圖須分層判斷

- 9/23 Client 原始 SD 已有與手機相差數十公尺的位置，不是 Station 地圖把點平移。
  當時報告以 4,786 個共同時刻比較，距離中位數 31.556 m、P95 84.811 m；手機沒有 accuracy／HDOP，不能視為測量真值。
- 7,382 個可配對 GPS epoch／TX 的 E7 解碼座標與本機記錄一致，只能證明該配對範圍的編碼一致。
  共存資料的 7,508 個成功 DATA TX 中，7,506 個在 Station 找到逐 byte 相同的已接受封包。
  99.97336% 是共同保存區間的配對率，不是全場 RF PER；不能用大量 RF 丟包解釋本機已存在的位置偏差。
- 9/24 診斷版已保存原始 NMEA。1,124 個有效 snapshot 與同 epoch NMEA 相符，772 個有效定位 DATA 的 E7 也吻合。
  與手機 UTC 配對後，停留中位距離／P95 為 1.20／3.31 m，移動為 8.46／22.33 m。
  測試條件、暖機、移動及重啟混在一起，不能據此認定改 1 Hz 已修好定位，或已排除 RF／SD 干擾。
- 改用座標差值只是編碼／airtime 選擇，不能消除接收器原有偏差；起點校正也不能消除隨時間變動的誤差。

### 2. RF 收到、DATA 新鮮與 GNSS fix 是三種狀態

- 9/23 開機前 10 分鐘已有 TEL／DIAG／GNSS DIAG，卻無定位 DATA；舊 OLED 以 DATA freshness 顯示 LoRa MISS。
  電量存在和 MISS 並不矛盾，也不能據此宣稱 RF 已斷線。保留狀態分層，不以放寬 GPS 門檻掩蓋等待。
- 10/6–7 的 T096 500 ms 時槽由 DATA、STATE 與診斷共用；30 秒 48 包 DATA 且序號連續可符合排程。
  不能把 1.6／2 包每秒當作 80% 收包率，降低 SF 也不會自動改變 DATA 排程。
  SF9 部署與 110 個 probe 無缺號的桌上驗證已在 `sf9-field-pair-2026-10-07` 紀錄中。
  當時 profile 不是今日設定，現役以交接文件與實機讀回為準。

### 3. 重啟缺口不能全算成 RF 漏包

- 9/23 至少六次非預期重啟：boot、uptime、DATA seq 歸零與 14–19 秒接收缺口互相印證。
  舊開機畫面能解釋恢復較慢，不能解釋重啟原因；當時 coredump 全 FF，缺 reset reason，根因未定。
- 9/24 外測三次非預期 boot，後兩次之前無 TX、SD 未供電；這排除「一定要正在 TX／寫 SD 才會發生」，
  不等於排除所有供電、接觸、按鍵或 PMU 問題。PMU latch 也可能是舊狀態。
- USB 桌上約三小時沒有重啟，45 次 SD 讀回的 CRC／SHA 通過，但有 81 秒交接觀察缺口，Flash 滿後不再保存新原始資料。
  USB 穩定不能代替純電池、移動或戶外驗收；SD 讀取壓力也不等於 SD 寫入壓力。

### 4. USB 匯出需要完整性與完成契約

- 9/23 首次匯出少 168 bytes；重新取回通過 size／CRC／JSON 檢查。
  從正確副本移除相同區段能重現破損，故是當次 USB 取回缺失，不能定為 SD 原檔壞掉。
- 9/24 的主機控制排程測試重現：worker 先輸出 END，還沒釋放 `usbActive`，下一命令已被 parser 消耗而靜默丟棄。
  實機 READ 沒有 header、boot 不變的症狀相符，但當時沒有直接量到內部 busy 時序。
- 等 500 ms 曾讓實機完成讀回，但固定延遲只是歷史 workaround，不是協定保證。
  持續原則是完成回覆後即可接受下一命令；現行回歸入口為 `tools/test_usb_completion.py`、`tools/test_sd_usb_budget.py`。
  本次整理沒有重跑或重新宣告實機修復驗收。

### 5. 軟體主動關機與電池供電故障要分開

- 9/24 兩個 boot 在約 12.782 秒記錄 long-press IRQ 後的 `shutdown/pwr_long_press`，並正常停止／sync。
  這是軟體主動關機的證據，不是突然斷電；當時 I2C read／clear failure 為零，也不是另一個 signed read -1 誤當按鍵的案例。
- signed PMU IRQ、clear failure 去重與 startup baseline／新按壓的邊界，需靠負例與按鍵時序驗證，不能把所有 PKEY 問題混成同一根因。
- 後來另出現拔 USB 立即失電、純電池無畫面。換電池、舊 app A/B 和冷斷電沒有恢復。
  最後原始 PMU 取樣報 absent、偵測／ADC 已開啟且該次讀取無失敗，把方向縮至電池座／連接／保護／供電路徑。
  `battery_mv=0` 不是電芯實測 0 V；沒有電表或導通量測，不能指認特定 IC、燒斷走線或宣稱所有軟體因素都排除。
- 長按修正已有歷史主機與 USB 部署證據；純電池／實體資訊頁顯示驗收仍有缺口。不可因新版 build 成功而改寫為全部通過。

- 清理僅針對家目錄三個指定目錄，不擴及現役 `~/.local/state/shore-spotter/` 的 11 月部署產物。

  Git 保存本文與既有紀錄，不保存這批 raw。舊報告中的絕對路徑及「已保存」是當時狀態，不能當作今日仍可重算的保證。

- PCB 現用重建來源與原 CAD 標籤應推到遠端；兩個 FCBak 是較早版本，另留本機，不冒充現用原圖。

- 工作目錄未追蹤的 `freecad/gps-antenna-case/` 不屬本次清理範圍；未因此宣稱它已受遠端 Git 保護。

## 後續固定做法

每次工作結束，把觸發條件、結論、理由、驗證層級、未解問題與必要重現方法寫進專案文件或測試。
不需保留的 raw 在摘要可取回後清理，不讓私人暫存路徑成為唯一知識入口。
commit 仍只在同一顆磁碟：須 push 並核對遠端 refs；只有本機的 tag 也不能算備份。
用遠端新 clone 執行紀錄校驗，實際匯出含圖片的紀錄，才確認新電腦可取回；私人憑證仍從範例重建或使用獨立私人備份。
