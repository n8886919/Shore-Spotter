# 現場除錯與匯出（0.6-dev）

先將 Client、Server 都更新為 LoRa v4 相容韌體，再重新整理 Server 網頁。
本版原始碼已實作診斷；編譯／主機測試不代表板上已更新或戶外測試通過。

## 錄製方式

1. 手機連上攝影站所在的熱點，開啟 OLED 顯示的網址，進入「除錯」。
2. 確認韌體／協定版本、綁定 Client ID，以及 DATA 接收計數持續增加。
3. 按「開始新紀錄」，在「測試備註」記下距離、測試動作與問題發生時間。
4. 完成後按「停止紀錄」→「匯出 JSON」，確認檔案已下載。可直接交給 AI 分析。
5. 下一段測試再按「開始新紀錄」。這會清空上一段錄製樣本，請先匯出。

若使用沒有本專案背景的 AI，請一併提供 [interface.md](interface.md)，讓它能正確解碼
自訂 v4 的 raw hex；僅憑「LoRa v4」無法知道本專案欄位定義。

錄製期間可以切到本站其他分頁。全頁 API 共用一個請求排程，控制優先；除錯每秒最多
取樣一次，忙碌時延後並記錄取樣缺口。最多 10 分鐘、1200 筆或
5 MiB **樣本資料**，先到者自動停止；JSON 縮排與目前快照可能讓下載檔稍大。
手機鎖屏、背景節流、Wi-Fi 斷線會漏採；系統會盡量留下間隔、逾時或覆寫提示。
**保持瀏覽器前景，重整或關閉前先匯出**；沒有瀏覽器錄製時，板上只保留有限近期紀錄。
停止錄製後，除錯頁的目前快照仍可更新；匯出檔會分開保存 `samples` 與 `current`。

## 可以檢查什麼

| 資料 | 用途 |
|---|---|
| RF 參數、DATA／ACK／TEL／DIAG 長度與 airtime | 確認雙端格式與排程設定；不是頻道掃描 |
| DATA 計數、序號缺口／重同步、RSSI／SNR、拒收原因 | 分辨無線遺失、錯誤格式、配錯 Client 或重複包 |
| 原始封包 hex、fix／向量有效旗標、來源 age | 重新解碼核對 17-byte 封包與定位新鮮度 |
| Server 本地 GNSS epoch 間隔／checksum／積壓 | 檢查岸上定位與讀取是否正常 |
| Client 低頻 DIAG：epoch 間隔、積壓、NMEA／TX 錯誤、跳過時槽 | 檢查下水端，約每 30 秒找空檔發送；未收到與過期會標示 |
| track／status 快照、α、速限、模式、控制計時、UART 統計 | 對照設定與目標變化；角度是命令值，沒有機械位置回饋 |
| 文字 log、Server boot ID、瀏覽器時間與取樣錯誤 | 對齊事件與辨識重啟、斷線或紀錄缺口 |

除錯 API 與瀏覽器匯出格式升為 `schema_version: 2`；更新 Server 後需重整網頁。
匯出 `kind: shore_spotter_diagnostics`，包含版本、設定、
備註、錄製統計、目前快照及逐次樣本。各 API 快照並非同時取得，檔案保留各自取得時間；
瀏覽器時間不等於 ESP32 `millis()`，跨重開機應按 `boot_id` 分段。
原始定位會包含在匯出檔；韌體的 Wi-Fi 帳密不會放進診斷設定，文字 log 也不印熱點名稱。

封包事件以 boot ID／事件游標增量讀取，每次最多 8 筆；首次開頁面的歷史資料分批補齊，
不會立即顯示全部 64 筆。瀏覽器合併近期事件供畫面顯示，錄製樣本只保存各次新增事件。
分析時不能再假設每筆樣本各自包含完整 64 筆歷史；跨重啟分段、依事件 ID 去重，並留意
`more`（尚有下一批）、`dropped`（游標落後／無效）及 `reset`（重新建立讀取起點）。

除錯頁也顯示最慢 HTTP 請求的路徑與分段耗時：解析／派送、組裝資料、同步寫入與其他。
這是已完成請求的板上時間，不是手機看到的整段等待時間；閒置或未完成解析的輪詢另計。
資料變小能減輕傳輸負擔，不能保證所有 Wi-Fi 條件下都沒有停頓。

## 現場優先確認

- **RF 2 Hz 與定位 2 Hz 分開看**：DATA 目標間隔 500 ms；Client DIAG 的
  `epoch_interval_ms` 才是模組觀察到的定位更新間隔，0 表示未知。
  「由接收封包推估」的來源間隔只是估計，不能取代 Client 端診斷。
- **年齡不能因重傳歸零**：追蹤看來源 age＋airtime＋接收後時間，再加 200 ms
  不確定度，必須未滿 2 秒。來源 age 以 NMEA epoch 對齊到達時間估計；
  GNSS 模組內部延遲尚未量測。
- **定位與外推分開看**：兩端 GPS 品質合格才可追蹤；速度／方向無效只停用外推。
  α 關閉也仍追最後有效位置。先靜止，再做短距離直行／折返，比對實際鏡頭行為與時間備註。
- **新 Server 綁定**：預設未綁定；既有 NVS 綁定保留。除錯頁顯示目前 ID 和最近被拒收 ID。
  如需首次設定，確認 Client OLED 的 ID，使用既有
  `POST /api/whitelist?action=set&id=<1–4位十六進位ID>`；詳見 [介面文件](interface.md)。

Server 的封包事件只有 **64 筆環形紀錄**，文字 log 為 **4096 bytes**；覆寫會計數，
不能回溯瀏覽器未錄製的整場資料。Client 診斷計數自其開機累計，最多 65535；
低頻快照可能晚到或遺失，沒有 Client boot ID，因此計數下降只能協助推測 Client 重啟。

可附這段給 AI：

> 請依此 JSON 的 protocol_version 與設定解碼 raw_hex；按 Server boot_id 分段，
> 區分來源定位年齡、RF 接收間隔與瀏覽器漏採。檢查定位品質、速度有效性、DATA 序號、
> Client DIAG、ACK／TX 錯誤和控制延遲，再對照我的測試備註。未知或過期資料請明確標示，
> 不要把軟體角度當成實體馬達位置。
